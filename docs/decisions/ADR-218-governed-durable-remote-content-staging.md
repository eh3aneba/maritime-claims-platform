# ADR-218 — Governed durable remote-content staging

**Status:** Proposed for Phase 17.5-N  
**Date:** 2026-09-16

## Context

Phase 17.5-M proves one bounded remote file-content read for one exact Phase L file item and then discards the bytes. The next authority increase needs durable custody without silently turning a remote item into a local Document or Evidence object.

The Phase 17.3 S3-compatible foundation is intentionally non-destructive: it exposes bounded PUT/conditional PUT/GET/HEAD only. Phase 17.4 likewise refuses S3 deletion. Phase N must preserve that permanent separation rather than introducing cleanup-by-delete.

## Decision

Phase N may stage exactly one Phase M-bound body into the existing `S3CompatibleEvidenceStore` foundation under a dedicated `external-remote-content-quarantine` namespace after an exact second-read reconciliation.

The execution first commits a tenant-scoped **requested recovery anchor** and requested receipt. The anchor fixes the exact Phase M completion hash/content proof and an application-generated deterministic opaque storage key. Only after that durable anchor exists may the provider body be re-read and conditionally written.

The second read must satisfy the same provider/source, item, size, media and version rules as Phase M and its SHA-256/byte count must exactly equal the completed Phase M proof. A conditional `put_bytes_if_absent` is followed by HEAD/GET verification of hash and size.

If the process fails after object creation but before DB completion, no destructive cleanup is attempted. Exact retry finds the committed requested anchor, reuses the same deterministic key, verifies the already-created object and completes the same execution. A mismatched object at that key fails closed.

## Authority granted

Phase N grants only durable quarantined custody of one exact body whose bytes have been cryptographically reconciled to one exact Phase M execution.

Persisted application facts are limited to lineage hashes, expected content SHA-256/byte count/media/version facts, sanitized storage-backend identity, internal storage key plus a safe key hash, timestamps, status and receipt hashes. The raw key is internal and is never returned or audited.

## Explicitly not granted

Phase N grants no:

- local Document creation or mutation;
- Evidence admission or Claim Fact creation;
- parsing, OCR, rendering, indexing or text extraction;
- synchronization, checkpoint, subscription or background polling;
- API download/body exposure or signed/public storage URL;
- provider upload/edit/move/rename/delete;
- object-store DELETE/COPY/lifecycle/migration authority;
- claim mutation or automated claims decision authority.

## Security and integrity rules

- Request input is only `request_key` and `reason`; provider identifiers, URLs, paths, headers, ranges, content and storage coordinates are rejected.
- The full A→M lineage is revalidated before anchoring, completion and later reads.
- Storage is fail-closed unless the governed Phase 17.3 S3 foundation is enabled/configured or an explicit bounded test seam is registered.
- The provider reread adapter kind and endpoint-policy hash must be identical to the completed Phase M execution.
- Object keys are generated by the application from tenant/execution/digest facts and never from provider filenames.
- Secrets, tokens, raw provider responses, provider download URLs, object-store credentials and staged bytes never enter DB body columns, receipts, audit payloads or API responses.
- Completed reads verify the quarantine object still reports the expected hash and size.

## Consequences

This creates a durable custody handoff without conflating storage with Document/Evidence authority and without broadening destructive object-store capabilities. Synchronization/checkpointing, Document creation and Evidence admission remain separate future authority increases with independent review, validation and merge authorization.
